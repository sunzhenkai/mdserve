## Why

桌面端文件树侧栏「收起后的展开按钮」与「关闭按钮」、以及大纲侧栏对应按钮的尺寸/样式不一致，视觉上不统一。同时大文档库下 `GET /api/files` 每次全量递归扫盘 + 前端一次拉取整棵树，导致目录树加载很慢；现状并非「启动预加载 + 内存增量更新」，有必要明确加载策略并做性能优化。

## What Changes

- 统一桌面端文件树与大纲侧栏的展开/关闭边缘按钮：尺寸、图标、透明度与 hover 行为以关闭按钮为基准对齐
- 服务端为可浏览文件树引入内存缓存：启动时构建，文件监听事件触发增量/重建更新，`/api/files` 优先读缓存
- 评估并落地分级按需加载（浅层列表 + 展开时拉取子树），作为大文件数场景的补充手段；小库可仍一次返回完整树
- 前端在树数据未就绪时保持现有加载态；`tree_reload` 后以缓存/增量结果快速刷新，避免每次全量卡顿

## Non-goals

- 不重做文件树交互（排序、定位、全部展开/折叠等业务逻辑不变）
- 不改动大纲内容树（Outline 标题层级）本身的数据结构
- 不引入持久化磁盘缓存或外部索引服务
- 不改变 ignore / 隐藏文件过滤语义与 MCP `list_tree` 的对外契约（除非为共享缓存做只读复用）
- 不做虚拟列表重构（若本轮缓存 + 按需加载已足够，则不强制虚拟化）

## Capabilities

### New Capabilities
- `sidebar-panel-toggles`: 桌面端文件树/大纲侧栏边缘展开与关闭按钮的视觉与交互一致性约定
- `file-tree-loading`: 可浏览文件树的加载、缓存与按需展开策略（含 `/api/files` 行为）

### Modified Capabilities
- （无）既有 `html-rendering` 中「HTML 出现在文件树」的需求不因本变更修改条文；实现仍须保证缓存结果与扫描语义一致

## Impact

- 前端：`App.tsx` 侧栏边缘按钮样式；`FileContext` / `FileTree` 的树数据获取与（若做按需）子节点加载
- 后端：`internal/docs` / `internal/server` 的 `ListTree`、`/api/files`，以及 watcher → `tree_reload` 与缓存失效/更新路径
- API：`/api/files` 可能新增可选查询参数（如 `path` / `depth`）；默认行为对现有客户端保持兼容
- WebSocket：`tree_reload` 语义保留，触发前端失效并读到更新后的缓存结果
