## Context

现状要点：

1. **侧栏边缘按钮**：文件树关闭按钮为 `w-4 h-11` + 图标 `h-3.5 w-3.5` + `opacity-40`；文件树收起后的展开按钮却是 `w-5 h-14` + 图标 `h-4 w-4` + `opacity-80`。大纲侧栏展开/关闭已接近关闭按钮规格，导致左右侧栏、展开与关闭之间视觉不一致。
2. **目录树加载**：前端启动时用 react-query 请求 `GET /api/files`；后端每次请求都走 `Library.ListTree()` 全量递归 `ReadDir`，**没有**启动预加载缓存。WebSocket `tree_reload` 只是让前端再打一次全量接口，等于每次变更都重新扫盘 + 传大 JSON。
3. **慢的根因**：大文档库下，首屏与每次 `tree_reload` 都付出「全量扫盘 + 大响应 + 前端全树 `sortFiles`/`collectAllPaths`」成本；UI 虽默认折叠，数据层仍是整棵树。

因此：用户以为的「启动预加载 + 动态更新」目前不存在；需要补上缓存，并引入分级按需加载改善首屏。

## Goals / Non-Goals

**Goals:**

- 统一桌面端文件树/大纲侧栏展开与关闭边缘按钮的尺寸与交互样式（以关闭按钮为基准）
- 服务端维护可浏览文件树的内存缓存：启动构建，监听变更后更新，读接口优先命中缓存
- 提供分级按需读取能力，前端默认按展开路径加载子节点，降低首屏与大库卡顿
- 深链打开文档时仍能展开并展示其父路径链上的节点

**Non-Goals:**

- 不改文件树业务交互（定位、全部展开/折叠语义）
- 不做磁盘持久化索引、不引入外部搜索引擎
- 本轮不强制虚拟列表（若按需加载后节点数仍过大，可另开变更）
- 不改变 ignore / 隐藏文件 / 空目录省略等扫描语义

## Decisions

### D1. 边缘按钮样式以「关闭按钮」为单一基准

- **选择**：文件树与大纲的展开/关闭边缘按钮统一为关闭按钮规格：`w-4 h-11`、图标 `h-3.5 w-3.5`、`opacity-40 hover:opacity-100 hover:w-5`（收起态展开按钮同样对齐，去掉 `w-5 h-14` / `opacity-80` 特例）。
- **备选**：以更大的展开按钮为准 → 拒绝，用户明确要求参考关闭按钮。
- **实现**：可在 `App.tsx` 抽共用 className 常量/小组件，避免四处漂移。

### D2. 服务端内存树缓存：启动预构建 + watcher 驱动更新

- **选择**：在 `Server`/`Library` 侧持有一份与 `ListTree()` 语义一致的内存树；启动时构建；收到目录结构变更时 debounce 后重建（或整树替换），`GET /api/files` 与 MCP `list_tree` 读缓存。
- **为何不全量增量补丁**：节点增删改路径多样，正确增量合并成本高；全量重建实现简单，配合 debounce（如 100–300ms）可合并抖动。大库重建仍可能贵，但调用方不再每次 HTTP 同步扫盘。
- **备选**：仅靠前端缓存 → 拒绝，无法消除服务端扫盘与大 JSON。
- **与「动态更新」的关系**：这才是真正的预加载 + 变更后刷新模型；`tree_reload` 仍通知前端失效查询，但后端响应应变快。

### D3. 要做分级按需加载（与缓存互补）

- **选择**：API 增加可选查询参数，例如：
  - `path`：相对 docs root 的目录（缺省为根）
  - `depth`：返回深度（`1` = 仅直接子节点；缺省或足够大时返回该节点下完整子树，保持现有客户端兼容）
- **前端策略**：
  - 初始只请求根层 `depth=1`
  - 用户展开目录时再请求该 `path&depth=1`，合并进本地树状态
  - URL/`currentFile` 深链：按父路径链并行预取各层，确保定位与展开可用
  - `tree_reload`：清空/失效按需查询缓存后按当前展开集重新拉取
- **为何缓存仍不够**：缓存加速重复读取与 reload，但**首次**全量构建与**全量下发**仍会拖慢首屏；按需加载把首包与前端处理量压到「可见层」。
- **备选**：只做缓存、前端仍一次吃整树 → 大库首屏与 `expandAll` 仍重；本变更至少支持按需路径，`expandAll` 可逐步拉取或在缓存就绪后拉一次全量（实现时择一，任务中写明）。

### D4. 兼容策略

- 无查询参数的 `GET /api/files`：**仍返回完整树**（来自缓存），保证旧前端/脚本/MCP 行为不变。
- 新前端改走按需参数；MCP 可继续用全量（读缓存）。
- HTML 文件进树、ignore 规则与现有 `html-rendering` 规格保持一致。

### D5. 缓存未就绪时的行为

- 启动后若首个请求早于首次构建完成：对该请求同步完成一次构建（或等待 in-flight 构建），避免返回空树；按需 `depth=1` 路径可走「仅扫目标目录一层」的快速路径，不必等待全量缓存（实现优先保证正确性，性能上浅层扫描本身应足够快）。

## Risks / Trade-offs

- **[Risk] 全量重建在超大库上仍可能尖刺** → debounce + 单飞（singleflight）；按需浅层接口不依赖全量重建完成。
- **[Risk] 按需合并状态与 `tree_reload` 竞态** → 以 generation/版本号或 invalidate 后按展开集重拉；避免陈旧子树残留。
- **[Risk] `expandAll` 触发大量请求** → 限制并发，或在全量缓存可用时一次拉全树。
- **[Trade-off] 实现复杂度上升**（缓存 + 按需）换首屏与大库可用性；小库用户几乎无感。

## Migration Plan

1. 先合样式统一（无行为风险）。
2. 后端加缓存与可选 `path`/`depth`，默认全量响应不变。
3. 前端切换为按需加载 + 深链预取。
4. 用中等/大文档目录验证：首屏时间、展开延迟、`tree_reload`、深链定位。

回滚：前端可回退为无参 `/api/files`；后端缓存为内部优化，关闭缓存逻辑即可回到同步 `ListTree()`。

## Open Questions

- `expandAll` 在按需模式下：批量浅层拉取 vs 一次全量——实现阶段按复杂度选更简单且正确的方案（倾向：缓存命中时一次全量）。
- 是否将「全量缓存构建」改为完全异步并在 UI 显示「索引中」：首版可不做独立状态，仅保留现有「正在加载文件列表...」。
